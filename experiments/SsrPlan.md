## Что решаем

В Next.js (App Router) клиентский компонент рендерится дважды: на сервере в HTML и в браузере при гидратации. Store не сериализуется, поэтому он создаётся дважды из одних и тех же props. Сейчас серверный проход отдаёт HTML без переводов и без данных и при этом запускает резолверы на сервере. Цель: первый HTML приходит с переводами и данными, сервер не делает запросов от имени store, гидратация проходит без расхождений и без повторного запроса.

Для этого нужны три свойства:

1. Всё нужное для первого рендера (контекст, транслятор, данные) попадает в конструктор синхронно, а не через `useEffect`.
2. Серверный проход ничего не запускает: ни резолверы, ни вход во flow.
3. Store создаётся на экземпляр компонента, а данные запроса нельзя положить в store уровня модуля.

Ограничения:

1. Корневой вход и subpath-входы только пополняются. Существующий код потребителей компилируется без правок.
2. `store/` на ветке не редактируется (правило CubePlan). SSR есть только в Cube; это первое намеренное расхождение реализаций.
3. Контракт (`cube/contract/**`) остаётся зелёным на обоих проектах. Тесты SSR живут в `cube/ssr/` и идут только в проекте `cube`.
4. Язык конфига не меняется. Новое — опции конструктора и React-обвязка.

## Как это выглядит для пользователя

```tsx
// app/[accountId]/customers/page.tsx — Server Component
export default async function Page({ params }: { params: Promise<{ accountId: string }> }) {
  const { accountId } = await params;
  const customers = await getCustomers(accountId);   // с cookies пользователя
  return <CustomersView accountId={accountId} customers={customers} />;
}
```

```tsx
// CustomersView.tsx
"use client";
import { usePalistor, useForm } from "palistor";

export function CustomersView({ accountId, customers }: Props) {
  const store = usePalistor(() => ({
    config: customersConfig,
    context: { accountId },
    initialData: { customers },
  }));
  const form = useForm(store);
  // ...
}
```

```tsx
// layout (клиентская обёртка): общие значения для всех store ниже по дереву
<PalistorProvider context={{ account, navigate }} translator={t} notifier={toast}>
  {children}
</PalistorProvider>
```

| Новое | Что делает |
|---|---|
| `new Palistor({ translator, notifier })` | транслятор и нотификатор с первого рендера, без `useEffect` |
| `new Palistor({ initialData })` | результаты резолверов, уже полученные сервером; узел с `resolve`, получивший данные, стартует как `resolved` |
| `new Palistor({ server })` | серверный режим: store ничего не запускает. По умолчанию `typeof window === "undefined"` |
| `store.start()` | запускает отложенное: вход во flow, eager-резолвы, lazy-резолвы, которые уже читали |
| `usePalistor(options \| () => options)` | один store на экземпляр компонента; подмешивает значения провайдера в конструктор и обновляет их при смене |
| `<PalistorProvider>` | `context`, `translator`, `notifier` для всех `usePalistor` ниже |
| `usePalistorContext()` | чтение `context` провайдера в компоненте (обычный React-контекст, реактивный) |

`useStoreContext`, `useTranslator`, `useNotifier` остаются и работают как раньше.

## Решения, которые принимаем сейчас

- **Серверный режим определяется окружением и перекрывается опцией.** `server` по умолчанию равен `typeof window === "undefined"`. Так серверные запросы исчезают и у существующих store, в том числе уровня модуля, без правок у потребителя. Отвергнуто: запуск резолверов из эффектов (сервер эффекты не выполняет, определять окружение не нужно). Он не закрывает eager-резолвы и вход во flow, которые стартуют в конструкторе, и ломает suspense: компонент, бросивший промис, не коммитится, его эффект не выполняется, и резолв не стартует никогда.
- **В серверном режиме store не стартует сам.** Ни eager, ни lazy, ни `onEnter` шага flow. Запрет стоит в одном месте (старт резолва и пейджера), а не в местах вызова. `store.start()` — явный запуск для скриптов и тестов в Node и точка, от которой позже можно сделать серверный prefetch.
- **Резолв, который запустится на клиенте, читается как `loading: true`.** Это eager-резолв и lazy-резолв после первого чтения, пока у них нет результата. Чтение `loading` списка и группы будит lazy-резолв так же, как чтение `items` и `value` (сейчас не будит: `cube/core/node.ts:84, 100, 161`). Без этого типичный код `if (list.loading) return <Skeleton />` на сервере читает `false` и отдаёт пустой список. Резолв, который ждёт `contextDeps`, остаётся `loading: false`, как в контракте. Узлы шагов flow не будят резолв (правило из Фазы 2.7).
- **Правило действует в обоих окружениях.** Первый клиентский рендер обязан совпасть с серверным, поэтому на клиенте `loading` тоже `true` между первым чтением и стартом в микротаске.
- **Suspense без данных на сервере отдаёт fallback границы.** Узел бросает ошибку с `digest: "BAILOUT_TO_CLIENT_SIDE_RENDERING"`: по ней Next молча отдаёт fallback и рендерит содержимое на клиенте (так работает `next/dynamic({ ssr: false })`; константа проверена в Next 16.0.10). Это внутренняя конвенция Next, поэтому она живёт в одной функции. Вне Next React тоже отдаст fallback, но запишет ошибку в лог сервера.
- **`initialData` — отдельная опция, а не расширение `initialValues`.** Сегодня группа с `resolve`, получившая `initialValues`, всё равно резолвится; смена этого смысла сломала бы существующий код. Форма `initialData` та же, что у `getValues()`: дерево значений, списки массивами строк, вложенные списки внутри строк. Для списка с пагинацией значение — массив или `PagedResult` первой страницы.
- **Состояние после `initialData` равно состоянию после того же результата резолвера.** Значения, baseline (`dirty: false`, `reset()` возвращает к этим данным), состав списков, статус `resolved`. Это и критерий приёмки: тест сравнивает два store.
- **`initialData` принимает только конструктор.** Метода «досыпать данные» нет. Store уровня модуля поэтому не может получить данные запроса, и утечка между пользователями исключена конструкцией API.
- **Зависимости резолва с `initialData` — только объявленные.** Резолвер на клиенте не запускался, автотрекинг его чтений неизвестен. Такой резолв перезапускается по `deps`, `contextDeps`, смене серверного ключа фильтра, ключу пагинации и `reload()`. Чтения, найденные автотрекингом, появятся после первого настоящего запуска.
- **Новые экспорты идут в корень.** Типы новых опций живут в `cube/`, фасадный тип конструктора расширяется в `cube/index.ts`. Когда появятся модульные входы ([ModulesPlan.md](./ModulesPlan.md)), `usePalistor`, `PalistorProvider` и `usePalistorContext` попадают в `palistor/core`.
- **Модули `cube/react/*` получают `"use client"`.** `tsc` сохраняет директиву в `dist`. Серверный файл тогда может импортировать из корня `Palistor`, `defineList` и типы: хуки для него становятся клиентскими ссылками и не исполняются.

### Этап 1. Конструктор и серверный режим

1. **Опции.** `translator`, `notifier`, `server` в `PalistorOptions`. Транслятор, нотификатор и контекст ставятся до построения дерева, чтобы вычисляемые значения и baseline считались уже с ними.
2. **`start()`.** Вход во flow и eager-резолвы переезжают из конструктора в `start()` (идемпотентный). Вне серверного режима конструктор зовёт его сам, поведение клиента не меняется.
3. **Запрет старта.** В серверном режиме до `start()`: `ResolveState.start()` и старт пейджера ничего не запускают, `touch()` запоминает резолв как прочитанный. `start()` запускает eager и прочитанные.
4. **`loading`.** Новое правило в `Cube.loading` и у пейджера; геттеры `loading` списка, группы и flow будят резолв.
5. **Сверка с контрактом.** В `cube/contract` 46 утверждений `loading).toBe(false)` в 18 файлах (срезы A, B, C, D, G, I, J; больше всего в C). Пройти каждое. Тест, который читает `loading` до данных и ждёт `false` или отсутствие запроса, фиксирует прежнее поведение: он идёт в список намеренных расхождений в CubeExperiment.md, а на проекте `cube` получает новое ожидание.
6. **Suspense.** Группа и список с `suspense: true` в серверном режиме без данных бросают ошибку с digest. Попутно: на клиенте первое чтение сейчас рендерит значения по умолчанию и уходит в fallback только после микротаска; проверить, можно ли бросать промис с первого чтения, не уведомляя подписчиков во время рендера. Если нельзя — оставить как есть и записать в журнал.

### Этап 2. React-обвязка

1. **`usePalistor`.** Принимает опции или функцию, возвращающую опции (вызывается один раз, чтобы `config()` не строился на каждый рендер). Создаёт store через `useState`. ### Этап 3. `initialData`

1. **Общие функции восстановления.** `restoreGroup`, `restoreList`, `restoreItemLists`, `rowData` выносятся из `persist.ts` в общий файл ядра с параметром «фиксировать baseline листьев и строк» (baseline состава списка `list.restore` ставит уже сейчас). Срез F контракта остаётся зелёным без правок.
2. **Применение в конструкторе.** Обход дерева по объекту `initialData`: лист получает значение и baseline; группа рекурсивно; список — строки в реестр, состав и его baseline, вложенные списки строк. Ключ, которого нет в данных, не трогается. Узел с `resolve`, для которого в данных есть значение, принимает начальные данные.
3. **Резолвы.** Статус `resolved`; зависимости — версии источников из `deps` и ключей `contextDeps` на момент создания. Лист шаблона списка уже покрыт существующим `skipIfResolved`.
4. **Пагинация.** Первая страница (`initialPage`) семейства текущего ключа принимает массив или `PagedResult` тем же кодом, что результат запроса. Следующая страница запрашивается как обычно. `revalidateOnHydrate` на эти данные не действует: они свежие.
5. **Фильтр.** После `initialData` серверный ключ фильтра считается уже запрошенным (`markIssued()`).
6. **Flow.** Вход в шаг с начальными данными: `onEnter`, затем сразу `onReady`.
7. **Предупреждения в dev.** Ключ, которого нет в конфиге; строка без `id`.
8. **Тип.** `InitialData<TConfig>` в `cube/`: частичное дерево значений, для списка с пагинацией — массив или `PagedResult`.

## Что не делаем

- **Запуск резолверов на сервере** (`await store.prefetch()` и `store.dehydrate()`). Он дал бы точные зависимости и убрал повтор запроса в серверной странице, но требует изоморфных резолверов; в palirent они берут браузерный клиент supabase напрямую. `store.start()` и форма `initialData` выбраны так, чтобы этот шаг позже лёг поверх без смены API.
- **Фоновую ревалидацию резолвов с `initialData`.** Она сняла бы ограничение про объявленные зависимости ценой одного лишнего запроса на резолв. Вернуться, если обкатка покажет, что `deps` приходится объявлять часто.
- **`<StoreProvider store>` и чтение store из дерева.** Типизированный контекст в приложении — три строки; библиотека добавила бы только нетипизированный поиск.
- **Замороженный серверный снимок для поздней гидратации.** См. риск про стриминг.
- **Данные как промис** (`use(promise)` и стриминг данных в store).
- **SSR в `store/`.** Реализация-эталон уходит в Фазе 4 CubePlan.
- **Перевод всего `app-demo` на `usePalistor`.** Только маршрут `/ssr`; остальное демо должно собираться на store.

## Открытые вопросы (решение за владельцем)

1. **Имя опции.** В плане `initialData`. Альтернативы: `resolved`, `seed`. Риск имени — близость к `initialValues`.
2. **Suspense на сервере.** В плане ошибка с digest Next. Альтернатива без внутренней конвенции: не бросать, отдать `loading: true` и значения по умолчанию.
3. **`loading` будит lazy-резолв.** Это меняет поведение и на клиенте. Без этого SSR-скелетон требует читать данные раньше `loading`, что неестественно для кода потребителей.
4. **Определение окружения по умолчанию.** В плане автоматическое с опцией `server`. Альтернатива: серверный режим только через `usePalistor`; тогда store уровня модуля у palirent продолжат ходить в сеть с сервера.
5. **Когда делать.** Рекомендация: Этапы 1–2 до Фазы 3 CubePlan, потому что они меняют поведение, которое обкатка должна проверить, и palirent тогда мигрирует один раз. Этапы 3–5 могут идти параллельно с обкаткой.
6. **Имя хука.** В плане `usePalistor`. Альтернатива: `useCreateStore`.
