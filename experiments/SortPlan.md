# План: сортировка списков, режим «Применить» и демо всего функционала списков

Дата: 2026-11-24. Основа: ветка `cube-architecture`, коммит `6f5a081`, версия `0.1.1-cube.2`. Статус на 2026-11-24: этапы 1–5 выполнены и закоммичены (итоги и отклонения — в строках «Статус» под заголовками этапов); Этап 6 не начат — публикация `0.1.1-cube.3` ждёт подтверждения владельца. Решения владельца от 2026-11-24 внесены: демо отдельным маршрутом, как `/ssr` (решение 16); порядок сам не перестраивается (решение 8); третье нажатие снимает сортировку (решение 9); публикация сразу следующей версией (Этап 6). Правка типов в `store/` (решение 15) сделана: команда «реализуй план» принята как разрешение на это исключение.

## Что решаем

Три задачи, по убыванию важности.

1. **Сортировка по полю.** Базовый случай: пользователь нажимает на заголовок колонки, и строки встают по значению этого поля. Второе нажатие меняет направление, третье возвращает исходный порядок. Автору конфига для этого хватает одной строки (`sort: true`), компоненту — одного вызова (`list.sort.toggle("price")`).
2. **Режим «Применить» для фильтра.** Поля фильтра становятся черновиком: список и запросы меняются только по явной команде (кнопка «Применить», Enter в поиске).
3. **Демо и проверка.** В app-demo появляется страница, где показан и покрыт e2e-тестом каждый пункт функционала списков: новый (сортировка, «Применить») и уже существующий, которого в демо сейчас нет.

Ограничения:

1. Существующий код потребителей компилируется и работает без правок. Список без блока `sort` и фильтр без `$apply` ведут себя как сейчас.
2. Новое есть только в Cube. Рантайм `store/` не меняется (правило CubePlan); про типы — решение 15.
3. Контракт (`cube/contract/**`) остаётся зелёным на обоих проектах. Новые тесты живут в `cube/core/`, `cube/react/`, `cube/ssr/` и идут только в проекте `cube`.
4. `npm run test:e2e:store` остаётся зелёным: его запускает CI.
5. Сортировка — проекция, а не мутация. Состав списка, `getValues()`, `dirty` и submit от неё не зависят, как и от фильтра.

## Как это выглядит для пользователя

### Базовый случай: нажатие на заголовок

```typescript
interface Product { id: string; title: string; price: number; category: string; inStock: boolean; rating: number | null }

const products = defineList<Product>({
  template: {
    id: { value: "" }, title: { value: "" }, price: { value: 0 },
    category: { value: "" }, inStock: { value: true }, rating: { value: null },
  },
  sort: true, // любое поле шаблона сортируется по своему значению
  resolve: { resolver: async () => api.products() },
});
```

```tsx
function ProductsTable({ products }: { products: PalistorList<Product> }) {
  const list = useForm(products);
  const sort = list.sort!; // как `filter`: в типе опционален, есть только у списка с блоком

  return (
    <table>
      <thead>
        <tr>
          <SortHeader sort={sort} column="title">Название</SortHeader>
          <SortHeader sort={sort} column="price">Цена</SortHeader>
        </tr>
      </thead>
      <tbody>{list.map((row, _index, id) => <ProductRow key={id} product={row} />)}</tbody>
    </table>
  );
}

type ProductKey = keyof Product & string;

function SortHeader({ sort, column, children }: { sort: SortProxyNode<ProductKey>; column: ProductKey; children: ReactNode }) {
  const state = useForm(sort);        // своя подписка: при смене сортировки перерисовываются заголовки
  const dir = state.dirOf(column);    // "asc" | "desc" | null

  return (
    <th aria-sort={dir === "asc" ? "ascending" : dir === "desc" ? "descending" : "none"}>
      <button onClick={() => state.toggle(column)}>
        {children}{dir === "asc" ? " ▲" : dir === "desc" ? " ▼" : ""}
      </button>
    </th>
  );
}
```

Запросов при этом нет: список без пагинации держит все строки и сортирует их сам. Порядок считается в момент нажатия и после этого сам не перестраивается: строка, которую добавили или изменили позже, остаётся там, где стоит, до следующей сортировки или загрузки (решение 8).

### Настройки блока

```typescript
sort: {
  $default: "-createdAt",                       // сортировка при создании; к ней возвращает reset()
  title: true,                                  // сортировка по значению поля
  customer: { by: (row: Order) => `${row.lastName} ${row.firstName}` }, // по вычисленному значению
  priority: { compare: (a: Order, b: Order) => RANK[a.priority] - RANK[b.priority] }, // свой порядок
  createdAt: { param: "created_at" },           // серверный список: имя параметра для сервера
}
```

Если в блоке не названо ни одного поля (`sort: true` или только `$`-опции), сортируемы все поля шаблона. Если названо хотя бы одно, сортируемы только названные.

### Серверная сортировка

Список с `resolve.pagination` держит одну страницу, поэтому сортирует сервер. Тот же блок, тот же `toggle`; сортировка приходит в резолвер и входит в ключ запроса.

```typescript
const orders = defineList<Order>({
  template: { id: { value: "" }, title: { value: "" }, amount: { value: 0 }, createdAt: { value: "" } },
  sort: { $default: "-createdAt", title: true, amount: true, createdAt: { param: "created_at" } },
  resolve: {
    pagination: { pageSize: 20 },
    resolver: async (_values: unknown, _store: unknown, ctx: ListResolveContext) => {
      let query = db.from("orders").select("*", { count: "exact" });
      for (const s of ctx.sort.by) query = query.order(s.param, { ascending: s.dir === "asc" });
      const { data, count } = await query.range(ctx.page!.offset, ctx.page!.offset + ctx.page!.pageSize - 1);
      return { items: data ?? [], total: count ?? 0 };
    },
  },
});
```

Нажатие на заголовок — один запрос первой страницы. Возврат к прежней сортировке при `maxCachedQueries > 1` отдаётся из кэша без запроса.

function FilterPanel({ filter }: { filter: FilterProxyNode }) {

## Решения, которые принимаем сейчас

**Сортировка**

1. **Блок `sort` включает сортировку.** Без блока у списка нет `list.sort`, ничего не выделяется и ничего не меняется. Так же устроены `filter` и `pagination`.
2. **Сортирует тот, у кого все строки.** Список без `resolve.pagination` сортирует сам (клиентский класс). Список с пагинацией отдаёт сортировку серверу (серверный класс). Опция `$server: true` переводит в серверный класс список без пагинации: для резолвера, который возвращает «первые N по порядку». Класс один на блок; смешивать клиентские и серверные поля в одном списке нельзя.
3. **Грамматика блока.** `true` или объект. Ключ с `$` — опция (`$default`, `$server`), остальное — поле. Значение поля: `true`, `{ by }`, `{ compare }` (клиентский класс) или `{ param }` (серверный). Конфиг, который не может сработать, бросает ошибку при создании store: `compare` / `by` в серверном классе, `param` в клиентском, неизвестная `$`-опция, `$default` по несортируемому ключу. Ключ поля — имя листа шаблона; лист во вложенной группе задаётся путём (`"address.city"`).
4. **Сортировка по значению.** Берётся значение поля из строки реестра (как `where` получает строку реестра). Числа сравниваются как числа, строки — через `Intl.Collator` с `numeric: true` и `sensitivity: "base"` («Товар 2» раньше «Товар 10», регистр не важен), `false` раньше `true`, `Date` — по времени. Значения разных типов сравниваются как строки.
5. **Пустые значения в конце в обе стороны.** `null`, `undefined` и `""` стоят после заполненных и при `asc`, и при `desc`.
6. **Порядок устойчив.** Равные строки сохраняют порядок состава. `desc` — это обратный знак сравнения, а не перевёрнутый массив.
7. **Проекция.** Видимые строки = сортировка(фильтр(состав)). `items`, `map`, `length` и итерация идут по ней. `getById`, `getValues()`, `dirty`, `store.getValues()` и submit остаются на полном составе в порядке состава. Клиентская нарезка на страницы у потребителя — `list.items.slice(from, to)`: порядок «фильтр → сортировка → страница» получается сам.
8. **Порядок считается в момент сортировки и сам не перестраивается** (решено владельцем 2026-11-24: перестраивать весь список при каждом изменении хуже, чем новая строка в конце). Клиентский порядок — снимок. Он пересчитывается в четырёх случаях: сменилась сортировка (`toggle` / `set` / `clear` / `reset`), пришла загрузка резолвера (список и так приходит заново), вызван `setItems`, вызван `sort.refresh()`. Между ними: строка, появившаяся в составе (`add`, строка из realtime-обновления), встаёт в конец; правка значения строку не двигает; ушедшая строка исчезает, остальные остаются на местах; `store.rekey` сохраняет место строки. Фильтр сужает снимок и порядок не меняет.
9. **Третье нажатие снимает сортировку.** `toggle(key)`: нет → `asc` → `desc` → состояние `$default` (без `$default` — порядок состава). Если это состояние совпадает с текущим, следующий шаг — `asc`. Подтверждено владельцем 2026-11-24.
10. **Поверхность `list.sort`:** `by` (массив `{ key, dir }`, пустой без сортировки), `key` и `dir` (первая запись или `null`), `keys` (сортируемые ключи), `dirOf(key)`, `toggle(key)`, `set(key, dir?)`, `clear()` (без сортировки), `reset()` (к `$default`), `refresh()` (пересчитать порядок по текущим значениям), `sortDescriptor` и `onSortChange` (формат React Aria / HeroUI). Запись в неизвестный ключ бросает ошибку.
11. **Серверный класс.** Резолвер получает `ctx.sort` всегда: `{ by: [{ key, param, dir }], key }`; без серверной сортировки `by` пуст и `key === ""`. Клиентская сортировка в `ctx.sort` не попадает: это описание работы сервера, как `ctx.filter.params`. Сортировка входит в идентичность запроса: обычный список запускает резолвер заново (`rs.invalidate()`), пагинированный меняет ключ запроса и грузит первую страницу. Смена сортировки во время запроса даёт один повторный запуск с последним состоянием. `initialData` считается ответом на `$default`: запроса после создания нет.
12. **Вне формы.** Состояние сортировки не попадает в `getValues()`, submit, persist и аргумент `values` резолвера; `store.reset()` его не трогает.
13. **Только корневые списки.** `sort` на списке внутри строки игнорируется с предупреждением в консоли, как сейчас `filter`.

**Режим «Применить»**

14. **`$apply: "manual"` делает поля блока черновиком.** `filter.<поле>.value` и `filter.values` показывают черновик. Проекция, `ctx.filter`, ключ запроса, `isActive` и `activeCount` считаются по применённым значениям. `filter.apply()` переносит черновик в применённые: одно уведомление и не больше одного запроса. `filter.revert()` возвращает черновик к применённым. `filter.isDraft` — черновик отличается от применённых. `filter.applied` — снимок применённых. `set` / `reset` / `clear` в ручном режиме пишут только черновик; применяет только `apply()`. Поле может переопределить режим блока: `apply: "auto"` или `apply: "manual"`. `debounce` на ручном поле бросает ошибку: запрос от ввода не уходит, опция не может сработать. В автоматическом режиме `apply()` и `revert()` ничего не делают, `isDraft === false`, `applied` равен `values`.

**Типы и демо**

15. **Типы правим в `store/store/types.ts` и `store/defineList.ts`.** Это единственное исключение из правила «`store/` не редактируется», и только для объявлений типов. Причина: `ConfigProxy`, `ListProxyNode` и `ListResolveContext` объявлены там, а зарезервированное `sort?: unknown` нельзя уточнить снаружи. На рантайме store блок `sort` молча отбрасывается (`store/defineList.ts` копирует только `resolve` и `filter`), а `$apply` бросает ошибку как неизвестная опция (`store/filtering/normalizeFilterBlock.ts:72`). Это второе намеренное расхождение реализаций после SSR.
16. **Демо — отдельный маршрут `/lists`, только Cube** (`src/app/lists/page.cube.tsx`, как `/ssr`). Вкладка Lists на главной собирается и на store, а конфиг с `$apply` на store падает при создании. Отдельный маршрут оставляет `test:e2e:store` зелёным без условий в коде демо. Вкладка Lists остаётся как есть и получает ссылку на `/lists` под тем же флагом, что и ссылка на `/ssr`. Подтверждено владельцем 2026-11-24: «как ssr».

Без этого `filter.apply()` и `sort.toggle()` в одном `batch` давали два запроса. Правка задевает и фильтр: таймер `debounce` теперь запускает запрос в том же тике, сразу после своего уведомления. Контракт фильтра и пагинации зелёный на обоих проектах.
- **Публичного `batch` нет.** «Сортировка и фильтр в одном `batch` — один запрос» достижимо только внутри библиотеки и в тестах (`store.hub.batch`). В обработчике `filter.set(...)` и следом `sort.toggle()` — два запроса; у пагинированного списка второй заменяет первый.
- **Быстрые нажатия.** Обычный список: изменения во время запроса дают один повторный запуск с последним состоянием. Пагинированный: каждое нажатие шлёт запрос и отменяет предыдущий — как ввод в поле фильтра без `debounce`.
- **Сортировка во время `debounce` фильтра** уносит ожидающее значение фильтра тем же запросом; `filter.isPending` при этом остаётся `true`, пока `debounce` не истечёт (остановить таймер можно только правкой `filter.ts`).

- **`refresh()` у серверного списка ничего не делает**; перезапросить — `list.reload()`.
- **Persist окна:** окно, сохранённое при сортировке не по умолчанию, не восстанавливается для store, который стартует с `$default` (он грузит первую страницу). Окно, сохранённое до появления блока `sort`, записи `$sort` не несёт и восстанавливается при любой сортировке — как и с `$filter`.

Находки по библиотеке (по правилу этапа не чинились, решение за владельцем):

1. **Persist окна списка не избавляет от запроса при перезагрузке.** `usePalistor` стартует store в эффекте и сразу запрашивает первую страницу; восстановление из `usePersist` асинхронно и приходит позже. Окно и якорь возвращаются, но один запрос уже ушёл. Утверждение «восстанавливается без запроса» верно, только если восстановление успевает до первого запроса (контрактный тест J1). Ручной старт (`server: true`, затем `persist.enable().then(() => store.start())`) тоже даёт один запрос: `start()` перезапрашивает уже восстановленную страницу.
2. **Перезагрузка с окном, сохранённым при другой сортировке, стоит два запроса.** Восстановление отвергает окно и при этом отменяет уже идущий запрос первой страницы, хотя он относился к действующему запросу; та же страница запрашивается снова.
3. **`setScrollAnchor` ничего не сохраняет сам:** он не меняет отслеживаемое состояние, якорь пишется со следующим изменением store. Демо вызывает `store.persist.flush()`.
4. **Якорь прокрутки переживает смену сортировки:** `scrollAnchor` сбрасывается только при восстановлении окна, не при смене запроса. Демо очищает его само.
5. **`$all` без единого поля с `where` не выполняется:** `hasClient` считается только по полям с `where`. Поле, которое читает только `$all`, становится серверным и перезапускает резолвер. Рабочий приём — `where: () => true` — был только в контрактном тесте.
6. **Результат `$toParams` не входит в идентичность запроса:** ключ строится по сырым значениям полей. `oslo` и `oslo ` дают два одинаковых запроса, на пагинированном списке ещё и сброс кэша страниц.
7. **`prefetch` устаревшей страницы заставляет клик ждать:** страница помечается как обновляемая, а `setPage` сразу показывает только свежие. Без наведения та же страница показывается из кэша и обновляется в фоне.
8. **`keepPreviousData`: состояние пейджера опережает строки.** Пока показаны прежние строки, `page` уже 1, `pageCount` — 0, `total` — `undefined`. Возможно, это вопрос дизайна, а не ошибка.
9. **Применить одно поле отдельно нельзя:** крестик на чипе (`clear(поле)` + `apply()`) применяет и остальной черновик панели. Это следствие решения 14.
10. **Проверка типов демо на store падала и до этой работы:** `npx tsc -p tsconfig.store.json` даёт 38 ошибок на чистой копии `6f5a081` (вызовы `useForm(field)`, которых типы store не принимают). На e2e store не влияет.

- **Клиентскую пагинацию в библиотеке.** Нарезка `list.items.slice()` даёт верный порядок (решение 7).
- **Готовые предикаты для `where`, отмену запроса через `ctx.signal`, счётчики по вариантам, `list.move`, выделение строк.**

## Открытые вопросы (решение за владельцем)

1. **Правка типов в `store/`** (решение 15). В CubePlan есть правило: папку `store/` на этой ветке не редактируем, чтобы не ловить конфликты при merge с `main`. Но описания типов узла списка и контекста резолвера лежат именно там, и Cube берёт их оттуда.
