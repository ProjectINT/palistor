# Эксперимент: Palistor на классах (Cube)

Дата: 2026-10-16. Набросок (с 2026-10-29 перенесён в [cube/core/](../cube/core/)): [index.ts в 90d8e67](https://github.com/ProjectINT/palistor/blob/90d8e67/experiments/index.ts).

Набросок проходит строгий tsc, а четыре сценария из README Palistor, прогнанные временным тестом, отрабатывают: реактивный isVisible, write pipeline с formatter и setter, optimistic и реальный resolve с перезапуском по зависимости, два списка поверх одного реестра сущностей.

## Мнение об идее

Идея хорошая, но выигрыш не там, где кажется. Сам Proxy занимает примерно две тысячи строк из шестнадцати. Громоздкость сидит в другом: в ручной машинерии зависимостей и в зоопарке видов узлов. Переход на классы даёт сократить объём, только если вместе с ним сделать две вещи.

- **Один рекурсивный примитив.** Лист, группа, список, элемент списка, шаг flow сейчас имеют по своему билдеру прокси и по своим веткам в ядре. В наброске это один класс плюс тонкий подкласс для списка. Resolve тоже один: на листе он резолвит информацию, на группе и списке резолвит кубики. Это ровно пункты 2 и 3 исходной идеи.
- **Автотрекинг через геттеры вместо карт зависимостей.** Каждый геттер кубика зовёт `track`. Одна глобальная переменная «кто сейчас наблюдает» закрывает вычисляемые флаги, зависимости resolve и трекинг чтений в useForm. У Palistor под это четыре разных tracking proxy, groupDepsMap, поле dependencies, топологическая сортировка и вся папка recompute. Ленивое мемо по версиям зависимостей заменяет их целиком.

Что при этом не исчезнет: pagination, persist, flows, filters, retry и типы. Это фичи, а не механизм. В новой архитектуре они становятся модулями вокруг ядра, но строки в них останутся.

## Слабые места наброска

- Трекинг в useForm без Proxy держится на том, что тело компонента выполняется синхронно до рендера детей. Чтения из компонентов без useForm попадут в набор последнего вызванного хука. Это лишний ререндер, а не баг, но точность Palistor теряется. Разумно оставить тонкий tracking proxy ровно в этом месте, остальной системе он не нужен.
- Spread полей в пропсы компонента перестаёт работать, потому что геттеры живут на прототипе. Нужен либо отдельный геттер `props`, либо own-enumerable геттеры.
- Зависимости асинхронного резольвера снимаются до первого await. Для чтений после него нужен values-объект, привязанный к наблюдателю, тот же трюк, что в createContextTrackingProxy, только на defineProperty.
- Зарезервированные имена детей остаются, как и сейчас: ребёнок с именем `submit` невозможен.
- Типизация через `CubeOf` набросана грубо, и типы в целом сильно не похудеют.

## Следующий шаг

Главный актив Palistor сейчас не код, а тесты: они и есть спецификация поведения. Разумный эксперимент на оценку идеи: портировать на Cube API один срез существующих тестов, например write pipeline и resolve, и посмотреть, сколько строк ядра понадобится, чтобы они позеленели.

### Расхождения, найденные в Фазе 0

1. **Submit и скрытые поля.** Store валидирует все листья, включая скрытые; исключение только для скрытых шагов flow (`filterHiddenFlowStepErrors`). Cube пропускает невидимые узлы в `collectErrors`. Контракт `surface.test.tsx` красный на `cube` ровно на этом. Решить в Фазе 1: баг Cube или намеренное изменение для документа миграции. Побочная находка: пример quick start в README (`passport.number` с `isRequired: true` внутри скрытой группы `passport`) на store не даёт отправить форму при оплате картой, пока не заполнен паспорт.
2. **`item.id` элемента списка.** В store это строка id сущности (README, раздел List proxy API). В наброске `id` — дочерний кубик. Шаг 2.1.
3. **API списков.** Store: `store.set(rows)` плюс `list.setItems(ids)`. Набросок: `setItems(rows)`. Шаг 2.1.
4. **`lazy: false` на списке.** Конструктор `Cube` запускает resolve внутри `super()`, до инициализации полей `ListCube` (`ids`, `cache`). Инициализаторы полей затем затирают оптимистичный результат. Фаза 1.

### Ядро после Фазы 1

`cube/core/`: `track` (Source, Signal, Observer), `memo`, `hub` (батч → один цикл уведомлений, подписки по узлу через версию состояния, переводчик, контекст с сигналом на ключ), `node` (публичный узел), `resolve`, `cube`, `listCube`, `registry`, `config`. Решения, отличающие его от наброска:

- **Публичный узел без Proxy.** `store.proxy.a.b` — обычный объект: собственные перечислимые геттеры ровно по spread-ключам store (`{...form.email}` отдаёт те же props), остальное — геттеры на прототипе, общем для всех узлов одного конфига; дети — неперечислимые геттеры там же. Члены класса `Cube` снаружи не видны, поэтому ребёнок `length` (palirent, `vehicleForm/parameters.config.ts`) — обычное поле. Зарезервированы ровно имена, которые proxy группы в store отвечал до поиска ребёнка (`value`, `submitting`, `dirty`, `revalidate`, `loading`, `values`, `submit`, `reset`, `setValues`, `onValueChange`, `label`, `placeholder`, `description`, `isVisible`, `isRequired`, `isDisabled`, `isReadOnly`, `isInvalid`, `errorMessage`): в store такой ребёнок был недостижим, в Cube конструктор бросает понятную ошибку.
- **Proxy только на границе `useForm`.** Tracking proxy записывает узлы, у которых компонент читал состояние; `getSnapshot` сравнивает их версии состояния. Версия состояния узла (`store.getNodeVersion`) растёт, только когда меняется что-то наблюдаемое (сигнатура: value, вычисляемые флаги и строки, dirty, ошибки, loading…), а не при каждом bump зависимости: это и даёт точность ререндеров store. Снимок `getSnapshot` стабилен внутри рендера. Массив `items` через границу оборачивается лениво: компонент, рисующий `items.slice(0, 100)`, платит за 100 строк.
- **Зависимости resolve после `await`.** Резольвер получает `values`, геттеры которого привязаны к наблюдателю запуска, и `store` с `context`, трекающим ключи. Изменение зависимости в полёте → перезапуск после завершения (`asyncContextInFlight` зелёный). Собственный результат резольвера за изменение не считается.
- **Утечки.** `remove` / `setItems` отвязывают view-кубики удалённых id от реестра и снимают их resolve с учёта. Поддерево элемента списка строится при первом обращении: 1 000 строк в реестре — это 1 000 лёгких кубиков, а не 1 000 × поля шаблона.
- **Один цикл уведомлений на действие.** `hub.batch` собирает запись, setter и patch в одно уведомление, как `recomputeAndNotify` в store; `getVersion` считает циклы.

### Расхождения Фазы 0 и новые

1. **Submit и скрытые поля** — баг наброска, исправлен: Cube валидирует все листья, как store. `surface.test.tsx` зелёный.
2. **`item.id`** — строка id сущности, собственное свойство узла элемента поверх ребёнка `id` шаблона.
3. **API списков** — `setItems` принимает и строки (id уже в реестре), и объекты (кладёт в реестр); `store.set(rows)` реализован для плоских строк с id. Остальное (`rekey`, `delete`, `invalidate`, вложенные списки, `useForm(entity, template)`) — шаг 2.1.
4. **`lazy: false`** — eager-резольверы стартуют после конструктора фасада, когда дерево построено.
5. **Новое, намеренное: зарезервированные имена детей** (список выше). Кандидат в документ миграции. Частичный grep по palirent и saas-starter (`submit`, `values`, `submitting`, `revalidate`, `setValues`, `onValueChange` как ключи конфигов) нашёл совпадения только в словарях i18n; окончательно покажет Фаза 3 — ошибкой конструктора.
6. **Новое, намеренное до 2.1: `{...item}` элемента списка** даёт только `{ id }` (store: `id`, ключи шаблона, `loading`, `submitting`, `submit`, `values`, `dirty`). Узлы элементов прототипные ради цены на тысячах строк. Решить в 2.1 вместе с поверхностью сущности.
7. **Найдено в store и повторено:** лист с `value: null` читается как `""` (`registerNodes`: `initialValues[key] ?? config.value ?? ""`). Зафиксировано в `sketchHoles.test.tsx`; кандидат в документ миграции на Фазу 4, если решить чинить.
8. `setContext` не уведомляет подписчиков (как store), но перезапускает резольверы, читавшие изменённые ключи, в том числе после `await`.

### Ядро после 2.1

`cube/` 2 699 строк (ядро 2 125, React 188, фасад и экспорты 386); после Фазы 1 было 1 658. Эквивалент store для этого шага — около 3 500 строк: `entityRegistry` 537, `buildListProxy` 732 (с ветками пагинации и фильтра, которых в Cube ещё нет), `buildEntityProjectionProxy` 400, `executeListResolve` 291, `executeEntityFieldResolve` 288, сущностная часть `palistor.ts` 731, сущностная часть `createResolveManager` ~430. JS `cube/` после tsc: 99 443 B, 24 834 B gzip (Фаза 1: 66 378 / 16 953).

Решения:

- **Строка в реестре плоская**, merge рекурсивный (как store), ключ, впервые появившийся в строке, засевает baseline для dirty. Baseline хранится на строке, не на view: две проекции одной записи согласны в `dirty`. Лист сущности хранит путь внутри строки (`rowPath`), поэтому группа внутри шаблона читает `row.profile.bio`.
- **Состояние resolve поля сущности общее на пару (id, конфиг)** (store: `EntityResolveStateMap`): элемент списка и форма `useForm(entity, template)` над одной записью запускают один резольвер и вместе видят `loading`. Снятый view отвязывается; состояние без views уходит из `hub.resolving` и возвращается с новым view; `store.delete` и `store.reset()` сбрасывают его.
- **View-кубик `useForm(entity, template)`** создаётся один на (id, шаблон) и живёт между монтированиями, как и `isResolved` в реестре. Resolve шаблона: `resolver(entityNode, store)` → merge в строку → `markResolved`; submit сущности: только `validate` листьев шаблона, `onSubmit(entityNode, store)`, `afterSubmit(result, { reset })` с пустым reset — ровно store.
- **Зарезервированные имена детей зависят от роли.** В группе формы — прежний список Фазы 1. В шаблоне сущности store отвечал сам только на `loading`, `submitting`, `submit`, `values`, `dirty`, а `label: { value: "" }` доставал как поле; в Cube ровно так: в шаблоне это ребёнок, в группе формы `label: { value: "Section" }` остаётся свойством группы (как store, где такой ребёнок был недостижим), и конфиг из `defineList.test.ts` строится.
- **Spread сущности = store**: `{...item}` даёт `id`, ключи шаблона, `loading`, `submitting`, `submit`, `values`, `dirty` (собственные перечислимые аксессоры, ~0,9 мкс на элемент; расхождение № 6 Фазы 1 закрыто). Spread листа сущности — ключи листа плюс `dirty`, `loading`, `submitting`, `submit`. У списка появился `Symbol.iterator`.
- **Граница `useForm`: два поколения прочитанных узлов** вместо «только растёт» (store копил все строки, которые список когда-либо показал). Чтение `item.id` трекает лист `id` строки (дешёвая сигнатура), а не кубик сущности: трекинг сущности на 100 строк стоил +1,5 мс на замену. Сигнатура группы без `validate` / `isRequired` не считает `isInvalid` / `errorMessage`.
- **`useStoreContext`** перенесён как есть (12 строк).

### Расхождения, найденные и намеренные

1. **Значения резольвера живые**, привязаны к наблюдателю запуска (так же для форм с Фазы 1): резольвер, читающий `values.x` после применения своего результата, видит новое значение; store отдавал снимок. Контракт читает внутри резольвера.
2. **Resolve поля сущности перезапускается по `setContext`** ключа, который он читал. В store контекстные зависимости записывались, но перезапуск шёл только по изменению путей сущности. Надмножество; в контракте нет.
3. **Результат resolve — новый baseline dirty и для листьев сущности.** В store `_setEntitiesRaw` писал значение сырым, `initialValueMap` оставался старым, и строки после повторного resolve показывали dirty-листья.
4. **`rekey` переписывает id и в начальном составе списка** (store — только в `itemIds`, список после rekey становился dirty). `delete` убирает id только из текущего состава, как store.
5. **Нестроковый `id` строки** → `String(id)` (store выдавал tmp-id). Пустой или отсутствующий → `_tmp_…`, как store.
6. **`entityRegistry` в Cube** — объект `Registry`: `get` (плоская строка), `has`, `size`, `bind` / `unbind` / `getBindings`, `markResolved` / `isResolved` / `clearResolved`, `ownerOf`, `getChildrenByOwner`. В store `get` отдавал узел `{ id: { value } , … }` с неперечислимыми `owner` и `lists`.
7. **Reset листа сущности из `afterSubmit`** сбрасывает один лист (store: `onReset` листа); reset листа формы — всю его группу (контракт Фазы 1).
8. **`values` сущности и `getValues` списка — по шаблону**, с `id` первым. В store `entity.values` собирались по всем ключам записи, включая те, что в шаблон не входят. Нетронутый вложенный список ключа не добавляет (как store); корневой всегда `[]`.
9. **Типы.** `typecheck:cube` исключает ещё девять файлов среза C: вложенный `defineList` или группа внутри типизированного шаблона не типизируются (`TemplateConfig`), react-оригиналы ставили `as any`. Та же категория, что `store.test.ts` в Фазе 1 — публичные типы, не контракт.
10. **Найдено в store: резольвер поля сущности, читающий своё же поле, перезапускается бесконечно.** Запись результата всегда идёт в `notifyChanged`, путь `_entity_.<id>.<field>` попадает в его собственные зависимости, а `_retriggerEntityFieldResolves` не имеет предела, в отличие от `MAX_AUTO_RETRIGGERS` корневых resolve. Так один контрактный тест (резольвер делал `{ ...values }`) ронял воркер vitest. Cube фиксирует зависимости до применения своего результата и не перезапускается. Тест читает только чужие ключи; кандидат в фикс `main`.
