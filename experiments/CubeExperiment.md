# Эксперимент: Palistor на классах (Cube)

Дата: 2026-10-16. Набросок (с 2026-10-29 перенесён в [cube/core/](../cube/core/)): [index.ts в 90d8e67](https://github.com/ProjectINT/palistor/blob/90d8e67/experiments/index.ts).

Набросок проходит строгий tsc, а четыре сценария из README Palistor, прогнанные временным тестом, отрабатывают: реактивный isVisible, write pipeline с formatter и setter, optimistic и реальный resolve с перезапуском по зависимости, два списка поверх одного реестра сущностей.

## Мнение об идее

Идея хорошая, но выигрыш не там, где кажется. Сам Proxy занимает примерно две тысячи строк из шестнадцати. Громоздкость сидит в другом: в ручной машинерии зависимостей и в зоопарке видов узлов. Переход на классы даёт сократить объём, только если вместе с ним сделать две вещи.

- **Один рекурсивный примитив.** Лист, группа, список, элемент списка, шаг flow сейчас имеют по своему билдеру прокси и по своим веткам в ядре. В наброске это один класс плюс тонкий подкласс для списка. Resolve тоже один: на листе он резолвит информацию, на группе и списке резолвит кубики. Это ровно пункты 2 и 3 исходной идеи.
- **Автотрекинг через геттеры вместо карт зависимостей.** Каждый геттер кубика зовёт `track`. Одна глобальная переменная «кто сейчас наблюдает» закрывает вычисляемые флаги, зависимости resolve и трекинг чтений в useForm. У Palistor под это четыре разных tracking proxy, groupDepsMap, поле dependencies, топологическая сортировка и вся папка recompute. Ленивое мемо по версиям зависимостей заменяет их целиком.

Что при этом не исчезнет: pagination, persist, flows, filters, retry и типы. Это фичи, а не механизм. В новой архитектуре они становятся модулями вокруг ядра, но строки в них останутся.

## Слабые места наброска

- Трекинг в useForm без Proxy держится на том, что тело компонента выполняется синхронно до рендера детей. Чтения из компонентов без useForm попадут в набор последнего вызванного хука. Это лишний ререндер, а не баг, но точность Palistor теряется. Разумно оставить тонкий tracking proxy ровно в этом месте, остальной системе он не нужен.
- Spread полей в пропсы компонента перестаёт работать, потому что геттеры живут на прототипе. Нужен либо отдельный геттер `props`, либо own-enumerable геттеры.
- Зависимости асинхронного резольвера снимаются до первого await. Для чтений после него нужен values-объект, привязанный к наблюдателю, тот же трюк, что в createContextTrackingProxy, только на defineProperty.
- Зарезервированные имена детей остаются, как и сейчас: ребёнок с именем `submit` невозможен.
- Типизация через `CubeOf` набросана грубо, и типы в целом сильно не похудеют.

## Следующий шаг

Главный актив Palistor сейчас не код, а тесты: они и есть спецификация поведения. Разумный эксперимент на оценку идеи: портировать на Cube API один срез существующих тестов, например write pipeline и resolve, и посмотреть, сколько строк ядра понадобится, чтобы они позеленели.

### Расхождения, найденные в Фазе 0

1. **Submit и скрытые поля.** Store валидирует все листья, включая скрытые; исключение только для скрытых шагов flow (`filterHiddenFlowStepErrors`). Cube пропускает невидимые узлы в `collectErrors`. Контракт `surface.test.tsx` красный на `cube` ровно на этом. Решить в Фазе 1: баг Cube или намеренное изменение для документа миграции. Побочная находка: пример quick start в README (`passport.number` с `isRequired: true` внутри скрытой группы `passport`) на store не даёт отправить форму при оплате картой, пока не заполнен паспорт.
2. **`item.id` элемента списка.** В store это строка id сущности (README, раздел List proxy API). В наброске `id` — дочерний кубик. Шаг 2.1.
3. **API списков.** Store: `store.set(rows)` плюс `list.setItems(ids)`. Набросок: `setItems(rows)`. Шаг 2.1.
4. **`lazy: false` на списке.** Конструктор `Cube` запускает resolve внутри `super()`, до инициализации полей `ListCube` (`ids`, `cache`). Инициализаторы полей затем затирают оптимистичный результат. Фаза 1.

### Ядро после Фазы 1

`cube/core/`: `track` (Source, Signal, Observer), `memo`, `hub` (батч → один цикл уведомлений, подписки по узлу через версию состояния, переводчик, контекст с сигналом на ключ), `node` (публичный узел), `resolve`, `cube`, `listCube`, `registry`, `config`. Решения, отличающие его от наброска:

- **Публичный узел без Proxy.** `store.proxy.a.b` — обычный объект: собственные перечислимые геттеры ровно по spread-ключам store (`{...form.email}` отдаёт те же props), остальное — геттеры на прототипе, общем для всех узлов одного конфига; дети — неперечислимые геттеры там же. Члены класса `Cube` снаружи не видны, поэтому ребёнок `length` (palirent, `vehicleForm/parameters.config.ts`) — обычное поле. Зарезервированы ровно имена, которые proxy группы в store отвечал до поиска ребёнка (`value`, `submitting`, `dirty`, `revalidate`, `loading`, `values`, `submit`, `reset`, `setValues`, `onValueChange`, `label`, `placeholder`, `description`, `isVisible`, `isRequired`, `isDisabled`, `isReadOnly`, `isInvalid`, `errorMessage`): в store такой ребёнок был недостижим, в Cube конструктор бросает понятную ошибку.
- **Proxy только на границе `useForm`.** Tracking proxy записывает узлы, у которых компонент читал состояние; `getSnapshot` сравнивает их версии состояния. Версия состояния узла (`store.getNodeVersion`) растёт, только когда меняется что-то наблюдаемое (сигнатура: value, вычисляемые флаги и строки, dirty, ошибки, loading…), а не при каждом bump зависимости: это и даёт точность ререндеров store. Снимок `getSnapshot` стабилен внутри рендера. Массив `items` через границу оборачивается лениво: компонент, рисующий `items.slice(0, 100)`, платит за 100 строк.
- **Зависимости resolve после `await`.** Резольвер получает `values`, геттеры которого привязаны к наблюдателю запуска, и `store` с `context`, трекающим ключи. Изменение зависимости в полёте → перезапуск после завершения (`asyncContextInFlight` зелёный). Собственный результат резольвера за изменение не считается.
- **Утечки.** `remove` / `setItems` отвязывают view-кубики удалённых id от реестра и снимают их resolve с учёта. Поддерево элемента списка строится при первом обращении: 1 000 строк в реестре — это 1 000 лёгких кубиков, а не 1 000 × поля шаблона.
- **Один цикл уведомлений на действие.** `hub.batch` собирает запись, setter и patch в одно уведомление, как `recomputeAndNotify` в store; `getVersion` считает циклы.

### Расхождения Фазы 0 и новые

1. **Submit и скрытые поля** — баг наброска, исправлен: Cube валидирует все листья, как store. `surface.test.tsx` зелёный.
2. **`item.id`** — строка id сущности, собственное свойство узла элемента поверх ребёнка `id` шаблона.
3. **API списков** — `setItems` принимает и строки (id уже в реестре), и объекты (кладёт в реестр); `store.set(rows)` реализован для плоских строк с id. Остальное (`rekey`, `delete`, `invalidate`, вложенные списки, `useForm(entity, template)`) — шаг 2.1.
4. **`lazy: false`** — eager-резольверы стартуют после конструктора фасада, когда дерево построено.
5. **Новое, намеренное: зарезервированные имена детей** (список выше). Кандидат в документ миграции. Частичный grep по palirent и saas-starter (`submit`, `values`, `submitting`, `revalidate`, `setValues`, `onValueChange` как ключи конфигов) нашёл совпадения только в словарях i18n; окончательно покажет Фаза 3 — ошибкой конструктора.
6. **Новое, намеренное до 2.1: `{...item}` элемента списка** даёт только `{ id }` (store: `id`, ключи шаблона, `loading`, `submitting`, `submit`, `values`, `dirty`). Узлы элементов прототипные ради цены на тысячах строк. Решить в 2.1 вместе с поверхностью сущности.
7. **Найдено в store и повторено:** лист с `value: null` читается как `""` (`registerNodes`: `initialValues[key] ?? config.value ?? ""`). Зафиксировано в `sketchHoles.test.tsx`; кандидат в документ миграции на Фазу 4, если решить чинить.
8. `setContext` не уведомляет подписчиков (как store), но перезапускает резольверы, читавшие изменённые ключи, в том числе после `await`.

### Расхождения, найденные и намеренные

1. **Значения резольвера живые**, привязаны к наблюдателю запуска (так же для форм с Фазы 1): резольвер, читающий `values.x` после применения своего результата, видит новое значение; store отдавал снимок. Контракт читает внутри резольвера.
2. **Resolve поля сущности перезапускается по `setContext`** ключа, который он читал. В store контекстные зависимости записывались, но перезапуск шёл только по изменению путей сущности. Надмножество; в контракте нет.
3. **Результат resolve — новый baseline dirty и для листьев сущности.** В store `_setEntitiesRaw` писал значение сырым, `initialValueMap` оставался старым, и строки после повторного resolve показывали dirty-листья.
4. **`rekey` переписывает id и в начальном составе списка** (store — только в `itemIds`, список после rekey становился dirty). `delete` убирает id только из текущего состава, как store.
5. **Нестроковый `id` строки** → `String(id)` (store выдавал tmp-id). Пустой или отсутствующий → `_tmp_…`, как store.
6. **`entityRegistry` в Cube** — объект `Registry`: `get` (плоская строка), `has`, `size`, `bind` / `unbind` / `getBindings`, `markResolved` / `isResolved` / `clearResolved`, `ownerOf`, `getChildrenByOwner`. В store `get` отдавал узел `{ id: { value } , … }` с неперечислимыми `owner` и `lists`.
7. **Reset листа сущности из `afterSubmit`** сбрасывает один лист (store: `onReset` листа); reset листа формы — всю его группу (контракт Фазы 1).
8. **`values` сущности и `getValues` списка — по шаблону**, с `id` первым. В store `entity.values` собирались по всем ключам записи, включая те, что в шаблон не входят. Нетронутый вложенный список ключа не добавляет (как store); корневой всегда `[]`.
9. **Типы.** `typecheck:cube` исключает ещё девять файлов среза C: вложенный `defineList` или группа внутри типизированного шаблона не типизируются (`TemplateConfig`), react-оригиналы ставили `as any`. Та же категория, что `store.test.ts` в Фазе 1 — публичные типы, не контракт.
10. **Найдено в store: резольвер поля сущности, читающий своё же поле, перезапускается бесконечно.** Запись результата всегда идёт в `notifyChanged`, путь `_entity_.<id>.<field>` попадает в его собственные зависимости, а `_retriggerEntityFieldResolves` не имеет предела, в отличие от `MAX_AUTO_RETRIGGERS` корневых resolve. Так один контрактный тест (резольвер делал `{ ...values }`) ронял воркер vitest. Cube фиксирует зависимости до применения своего результата и не перезапускается. ### Расхождения, найденные и намеренные

1. **Найдено в store: очистка снимка после успешного submit отменяется.** `persist.clear()` идёт до уведомления `submitting: false`, а оно планирует запись: через debounce отправленные значения снова в хранилище (с `debounce: 0` хранилище не пустеет ни на миг). `flush` при размонтировании `usePersist` пишет их же. Черновик воскресает после перезагрузки — ровно то, от чего очистка защищает. Контрактный тест store смотрит хранилище сразу после submit и этого не видит. В Cube `clear()` запоминает текущий снимок как учтённый: пока значения не изменились, запись пропускается, следующая правка — новый черновик. С `afterSubmit: reset` хранилище остаётся пустым, а не с дефолтами. Кандидат в фикс `main`.
2. **Найдено в store: встроенные драйверы глотают ошибки.** `localStorageDriver.setItem` молча ловит `QuotaExceededError`, поэтому квота никогда не доходит ни до `onError`, ни до повтора с урезанной пагинацией — хотя `PersistOptions` описывает оба ради неё. `getItem` при ошибке отдаёт `null`. В Cube драйвер проверяет только наличие хранилища (SSR), ошибки уходят менеджеру, тот отдаёт их в `onError` и в приложение не пропускает. Кандидат в фикс `main`.
3. **Намеренное: снимок, равный уже записанному, повторно не пишется.** Store писал на каждый цикл уведомлений: submit с ошибками валидации — две лишние записи того же самого (проверено: 4 вызова `setItem` против 2), смена статуса resolve — тоже. Первый цикл после `enable` пишет всегда: что лежит в хранилище, неизвестно.
4. **Намеренное, мелочи гидрации.** Повтор id в восстанавливаемом списке схлопывается, как в `setItems` (store клал id в состав дважды). Строка реестра теряет ключи вложенных списков на любой глубине (store вырезал только верхний уровень: список в группе шаблона оставался массивом внутри строки). `getItem`, вернувший `undefined`, значит «снимка нет» (store отдавал его в `JSON.parse` и звал `onError`).
5. **Отложено:** повтор записи с урезанными окнами пагинации при квоте — шаг 2.5; без пагинации в Cube одна попытка (store трижды писал одно и то же). Ключи `__flows` и `__pagination` при гидрации отбрасываются до 2.7 и 2.5.
6. **Как store:** `pick` / `omit` фильтруют только запись, гидрация применяет весь снимок. `$persist` фильтра принимается и ничего не делает: store его тоже не применял (блоб `__filters` — Фаза 2 FilteringPlan, не выпущена). Поля формы после гидрации dirty относительно конфига (`applyPatch` не двигал baseline), состав списков — нет.

1. **Найдено в store: пагинированный список перестаёт следовать за полем формы после 10 смен.** Каждый перевыбор семейства по зависимости считается в `MAX_AUTO_RETRIGGERS` (10), а счётчик сбрасывают только переход по странице и `setContext`. ### Контракт

Первое чтение запускает ленивый resolve на следующей микрозадаче, не внутри чтения; чтения во время прогона ничего не запускают. При `suspense: true`, пока прогон в `pending`, чтение детей, `value`, `label` и флагов группы бросает промис прогона (один и тот же объект); `loading`, `values`, `dirty`, `submitting`, `revalidate` и методы не бросают; первое чтение (idle) не бросает. Промис оседает, когда прогон приземлился, и не реджектится при ошибке резольвера; ошибки не бросаются. При `retry` промис покрывает все попытки. `optimisticResolver` suspense не отменяет. Зависимость, сменившаяся во время прогона: после первого промиса чтение бросает промис следующего прогона. Корневой resolve тоже suspends. Лист сущности не suspends ни с какими опциями.
- `suspense.react.test.tsx` (6) — `<Suspense>` через границу `useForm`. Компонент, смонтированный во время прогона, показывает fallback, потом результат. Компонент, читающий только детей, при перезапуске остаётся на прежнем содержимом (см. открытый вопрос). Без `suspense` компонент рисует `loading`. Соседний `useForm` вне границы не suspends.
- `contextDeps.test.ts` (9) — ленивый resolve до появления ключа не запускается и стоит в idle (`loading` false). `setContext` с ключом запускает его сразу. Посторонний ключ, `null` и `undefined` не запускают, `0` запускает. Нужны все ключи. Непрочитанный ленивый resolve при появлении ключей стоит на месте. Ключ пропал: resolve переходит в idle с прежним результатом, смены зависимостей в это время ждут, возврат ключа — один прогон с текущими значениями.

Список игнорирует `retry` и `optimisticResolver`, `reload()` — его повтор. Цепочка: resolve, читающий результат другого, перезапускается после него один раз на смену. ### Открытый вопрос (обе реализации)

## SSR: серверный режим, `usePalistor`, `initialData` (2026-11-23)

План: [SsrPlan.md](./SsrPlan.md). Сделаны Этапы 1–5. Этап 6 (пререлиз и обкатка на legends-core и palirent) не начат: публикация ждёт подтверждения владельца.

SSR есть только в Cube: `store/` не редактировался, контракт зелёный на обоих проектах. Это первое намеренное расхождение реализаций.

### Что сделано

- **Конструктор.** Опции `translator`, `notifier`, `server`, `initialData`. Транслятор, нотификатор и контекст ставятся до построения дерева. `store.start()` запускает то, что раньше запускал конструктор: вход во flow, затем eager-резолвы. Вне серверного режима конструктор зовёт его сам.
- **Серверный режим.** `server` по умолчанию `typeof window === "undefined"`. До `start()` ничего не запускается. Запрет стоит в трёх местах, где начинается работа: `ResolveState.start()`, `Pager.fetch()`, `FlowCube.enterCurrent()`. `touch()` запоминает прочитанный резолв в `hub.deferred`; туда же конструктор кладёт eager-резолвы, а flow — резолв активного шага. `start()` входит во flow и запускает всё из `hub.deferred`. Путь один для клиента и сервера: на клиенте `start()` идёт сразу за конструктором.
- **`loading`.** `Resolving.due`: запуск запланирован на микротаск либо отложен серверным режимом. `loading` = `pending || due`. Резолв, который ждёт `contextDeps`, не `due`. Геттеры `loading` группы, списка и flow будят lazy-резолв через `Cube.wake()` (без suspense); `loading` шага flow не будит.
- **Suspense.** Группа и список с `suspense: true` в серверном режиме без данных бросают ошибку с `digest: "BAILOUT_TO_CLIENT_SIDE_RENDERING"` — одна функция `clientOnly()` в `cube/core/resolve.ts`.
- **`initialData`.** Общий обход `cube/core/restore.ts` для persist и для конструктора: `restoreGroup`, `restoreList`, `restoreItemLists`, `rowData` переехали из `persist.ts`. Режим «результат» дополнительно фиксирует baseline листьев и помечает резолвы принятыми: `ResolveState.accept()` (статус `resolved`, зависимости — версии `deps` и ключей `contextDeps`), `Pager.accept()` (первая страница через тот же `ingest`, что и результат запроса). Сначала заполняются страницы, потом принимаются резолвы: их зависимости — версии после применения всех данных.
- **React.** `usePalistor`, `PalistorProvider`, `usePalistorContext`; `"use client"` во всех модулях `cube/react/`. Типы новых опций, экземпляра со `start()` и `InitialData<TConfig>` — в `cube/types.ts`.
- **Демо.** Маршрут `/ssr` только на Cube: `page.cube.tsx`, расширение `cube.tsx` в `pageExtensions` без `PALISTOR_IMPL=store`, каталог исключён в `tsconfig.store.json`.
- **Документация и skills.** Раздел «SSR & Next.js» в обоих README, skill `palistor-ssr`, проверка задачи `tests/skills/ssr-server-list/`.

### Намеренные изменения поведения (кандидаты в «Migrating to 0.1»)

1. **Без `window` store ничего не запускает сам.** Скрипт или тест в Node без DOM не получит данных, пока не вызовет `store.start()` или не передаст `server: false`. В jsdom ничего не меняется.
2. **`loading` равен `true` с первого чтения lazy-резолва**, а не с момента старта прогона (микротаск после чтения). У eager-резолва и резолва активного шага в серверном режиме — с создания store. `resolveStatus` по-прежнему `"idle"` до старта.
3. **Чтение `loading` группы, списка и flow будит lazy-резолв.** Раньше будило только чтение данных. То же у `isInitialLoading` пагинированного списка.
4. **Группа и список с `suspense: true` в серверном режиме без данных бросают ошибку** вместо рендера значений по умолчанию.

### Отличия от плана

1. **`isInitialLoading` пагинированного списка** тоже учитывает `due` и будит резолв. План называл только `loading`, но README рекомендует для скелетона пагинации именно `isInitialLoading`; без этого сервер отдавал бы пустой список. `isFetching` остался фактом транспорта: `false` до реального запроса.
2. **Флаги хаба.** Вместо «`server`, `started` и списка прочитанных до старта» — `held`, `started` и `deferred`, куда попадают и eager-резолвы, и резолв активного шага. `due` в серверном режиме тогда один вопрос: «есть ли резолв в `deferred`».
3. **Какая группа считается получившей данные.** План: «узел с `resolve`, для которого в данных есть значение». Для группы уточнено: в данных есть значение хотя бы одного листа под ней вне списков. Результат группового резолвера до списков не доходит (`patch` их пропускает), поэтому `initialData: { customers: [...] }` не помечает корневой `resolve` выполненным; `{ car: {} }` тоже.
4. **Flow.** Признак `seeded` на `ResolveState` переживает перезапуск по зависимости: шаг с данными, чья объявленная зависимость изменилась до первого входа, всё равно получает `onReady` на входе (после приземления прогона). Найдено тестовым агентом, в плане случая нет.
5. **`markIssued()` после `initialData`.** Обоснование в плане («иначе фильтр сразу запросит данные заново») неточно: gate срабатывает только при смене версии серверного поля, и запроса сразу после создания нет и без него. Реальный эффект один: ввод и откат внутри debounce не дают запроса. Вызов оставлен.
6. **`usePalistor` создаёт store через ленивый ref**, а не через инициализатор `useState`. На React 19.2 инициализатор `useState` под `StrictMode` вызывается дважды: два store, eager-резолвер и `onEnter` шага по два раза. Ленивый ref в том же замере дал один store. Требование плана — «один store на экземпляр, в том числе под `StrictMode`».
7. **`PalistorProvider` не в корневом layout демо.** Корневой layout общий со сборкой на store, а отдельный `layout.cube.tsx` дал расхождение сгенерированных типов маршрутов между реализациями (`tsc` демо зависел от того, какая сборка шла последней). Провайдер рендерит сама страница: `page.cube.tsx` → `SsrProviders` → `SsrView`.
8. **Baseline строк.** `list.restore()` и реестр и так фиксируют baseline новой строки; отдельного прохода «зафиксировать baseline строк» нет. Одна и та же строка в двух списках с разными значениями получает значение последнего и baseline первого — как после двух резолверов.

### Suspense с первого чтения на клиенте (Этап 1, п. 6): оставлено как есть

Бросать промис с первого чтения технически можно: промис создаётся в `touch()`, подписчики не уведомляются. Мешает другое. Компонент, который уходит в suspense до первого коммита, теряет состояние хуков, в том числе store из `usePalistor`. React при повторе создаёт новый store, тот снова читает и снова бросает. Замер на eager-группе с `suspense: true`, прочитанной в компоненте, который зовёт `usePalistor`: 26 store и 26 запросов за 12 тиков. С хуком выше границы `<Suspense>` и чтением в дочернем компоненте — 1 и 1. Lazy-группа в том же компоненте работает только потому, что первое чтение не бросает. Правило записано в JSDoc `usePalistor`, README и skill: узел с `suspense: true` читается в компоненте ниже границы, а не в том, который создаёт store.

Следствие для SSR: сервер отдаёт fallback, клиент после гидратации монтирует границу как всегда. Компонент, который читает только детей группы, показывает значения по умолчанию, пока данные не придут; в fallback он уходит, только если читает состояние самой группы (`loading`). Последовательность может быть «fallback → значения по умолчанию → данные». С `initialData` этого шага нет. Это довод к открытому вопросу 2 плана: альтернатива «не бросать, отдать `loading: true` и значения по умолчанию» дала бы серверу тот же первый кадр, что у клиента.

### Найдено по пути

1. **Обе реализации, до этой работы:** страница с `nextCursor: null` даёт `hasNextPage: true` в режиме `cursor` (`cube/core/pagination.ts`, геттер `hasNextPage`: записанный курсор следующей страницы проверяется через `has`, а не на `null`; то же в `store/pagination/paginationController.ts`). Тест конца ленты поэтому передаёт `hasMore: false`. Кандидат в фикс.
2. **Вне Next** гидратация границы, от которой сервер отказался, зовёт `onRecoverableError` один раз на границу; обработчик Next этот digest игнорирует. Без границы `<Suspense>` ошибка отказа фатальна для серверного рендера.
3. **Пейджер не смотрит `contextDeps`** (как и раньше): пагинированный список с `initialData` перезапускается по `deps`, фильтру и `reload()`.
4. **`contextDeps`, ключ которого пришёл после создания store** (`useStoreContext` в эффекте), считается сменой и запускает резолвер сразу после гидратации. Контекст нужно передавать в конструктор или провайдер.
5. **Первая страница длиннее `pageSize`** принимается целиком без предупреждения; `setPage(2)` запрашивает обычный offset.
6. **Серверный режим, `setPage(2)` до `start()`:** запроса нет, `page` равен 2, строки первой страницы, `loading: false`; `start()` грузит вторую страницу. Навигация по списку до `start()` на сервере не ожидается.
7. **Серверный режим, шаг с данными, зависимость сменилась до `start()`:** `start()` входит во flow раньше, чем запускает отложенные резолвы, поэтому `onReady` приходит с серверными данными до перезапуска, а не после него, как на клиенте. Нужна запись в store до `start()`; теста нет.
8. **Типы (store, на ветке не редактируются):** в типе `resolve` у `defineList` нет `contextDeps`, хотя ядро Cube его понимает у списка без пагинации; `list.filter!.search` типизируется как `any`. Skill советует `key` на компоненте вместо контекстной зависимости списка.

### Открытые вопросы (решение за владельцем)

1. **Store из отброшенного рендера.** Найдено на демо: при клиентской навигации на `/ssr` под нагрузкой store иногда создаётся дважды, и каждый lazy-резолвер без данных вызывается дважды. Замер: навигация в dev при четырёх параллельных браузерах — 8 из 48, production-экспорт при шести — 5 из 90, один браузер — 0 из 27; гидратация — 0 из 162. Механизм: навигация рендерится в transition; чтение в рендере планирует прогон на микротаск; если рендер уступил управление до коммита, прогон стартует и меняет снимок `useSyncExternalStore`; React перерисовывает дерево заново, а несмонтированный компонент теряет хуки вместе со store. Это свойство любого store на экземпляр, который запускает запросы из рендера (у legends-core с `useState(createStore)` так уже сейчас). Список с `initialData` запросов не делает в обоих случаях. В e2e случай записан как `test.fixme`.
   Вариант решения: `usePalistor` держит store до первого коммита и зовёт `store.start()` в эффекте. Механизм серверного режима для этого уже есть (`hub.held`, `hub.deferred`, `due`): первый клиентский рендер тогда совпадает с серверным по построению, отброшенный рендер ничего не запускает, eager-резолвы и вход во flow идут через тот же `start()`. План отверг запуск из эффектов по двум причинам. Первая (eager и flow стартуют в конструкторе) с `start()` снимается. Вторая (компонент, бросивший промис, не коммитится) остаётся только для чтения узла с `suspense: true` в самом компоненте с `usePalistor`; на клиенте удержанный store не должен бросать ошибку отказа, первое чтение отдаёт значения по умолчанию, как сейчас. Заодно уходит бесконечный цикл eager + suspense в компоненте-владельце. Это меняет решение плана, поэтому не сделано.
   **Решено владельцем 2026-11-24: делать до обкатки** — [SsrPlan.md](./SsrPlan.md), Этап 5а, п. 1.
2. **Suspense на сервере** (вопрос 2 плана). Замер на демо: fallback с сервера на 23-й мс, значения по умолчанию с 245-й, данные на 1052-й. Демо обходит это чтением `summary.loading` в компоненте под границей. См. раздел выше.
3. **Вопросы 1, 3, 4, 6 плана** (имя `initialData`, `loading` будит резолв, определение окружения по умолчанию, имя `usePalistor`) реализованы как в плане; сверка контракта вопрос 3 не опровергла: изменились 8 утверждений, все — чтение `loading` до данных.

### `server: true` в `usePalistor`: ручной режим

Решение, которое план оставил реализации. Хук с явным `server: true` store не запускает: `store.start()` зовёт вызывающий код. Причина: `server: true` в браузере — это просьба вести себя как сервер, а единственный способ выйти из серверного режима — явный `start()`. На этом построен блок 1 маршрута `/ssr/runtime`. Без опции и с `server: false` хук ведёт себя одинаково: строит store удержанным и запускает в эффекте. Различие `server: false` и умолчания остаётся только в Node: с `server: false` узел с `suspense: true` не бросает ошибку отказа. Эффект запускает store и там, где `window` нет, а эффекты есть (рендерер тестов в node-окружении): эффект выполнился, значит рендер закоммичен и это не сервер.

### Отличия от плана

1. **Старт прогона у группы с `suspense: true` стал наблюдаемым изменением** (`Cube.signature()` добавляет признак `pending`). Без этого eager-группа с `suspense: true` в store из хука на клиентском монтировании не доходила до fallback вообще: до старта `loading` уже `true` (резолв в `deferred`), после старта тоже `true`, сигнатура не менялась, компонент не перерисовывался и промис бросить было некому. Замер кадров до правки: `true:` → `false:BMW`, без fallback; после: `true:` → fallback → `false:BMW`. У lazy-группы и у списка этого пробела не было. Компонент, который читает только детей группы и не читает её `loading`, стартом по-прежнему не перерисовывается (общее ограничение обеих реализаций, срез J): на клиентском монтировании он показывает значения по умолчанию до прихода данных. Раньше у eager-группы с хуком выше границы он уходил в fallback сразу. Записано в README и skill: под границей читать `loading` узла либо дать `initialData`.
2. **П. 2 шире геттера.** `setPage(n)` и `prefetch(n)` в режиме `cursor` за концом ленты тоже ничего не запрашивают: иначе уходил запрос с `cursor: null`, то есть голова ленты под номером следующей страницы. Записанный `null` в `fam.cursors` больше не считается курсором: страница, которую перезапросили и получили уже без поля, возвращается к прежнему правилу, а не к своему старому `null`.
3. **П. 3: условие шире, чем «страница запрошена или вот-вот будет».** Молчим ещё и когда статус пейджера не `resolved`: после упавшей первой страницы `reset()` или локальная правка писали то же предупреждение. `project(issuing)`: вызывающий сообщает, что запрос уйдёт сразу после проекции.
4. **П. 4 и п. 6: `reset()` не доходил до вложенных списков без живого view.** `resetEntities()` обходил `hub.lists`, то есть живые кубы. Членство вложенного списка живёт с владельцем (`hub.entityLists`) и переживает свой view: у строки на другой странице пагинированного списка правка после `reset()` оставалась. С п. 6 это стало бы видно как «форма dirty после reset». Теперь `resetEntities()` дополнительно обходит `hub.entityLists`. Тест: «a nested edit on a cached page that is off screen keeps the list dirty; reset clears it».
5. **П. 5: тип контекста оставлен на Фазу 4.** Рантайм отдаёт `t` везде. Тип `ResolveErrorContext` берётся из `store/` и остаётся `{ notify }`. Перегрузка не ложится по двум причинам. Расширить интерфейс обязательным `t` через augmentation нельзя: исходники `store/` строят контекст литералом `{ notify }` и перестанут компилироваться. У `defineList` тип контекста записан прямо в сигнатуре (`{ notify: (msg: string) => void }`), а под `strictFunctionTypes` колбэк с более широким параметром к нему не присваивается. Проверено пробой под `typecheck:skills`: у группы в обычном объекте конфига аннотация `{ notify, t }: { notify: NotifyFn; t: TranslateFn }` компилируется; внутри `defineList` нужен cast `ctx as ResolveErrorContext & { t: TranslateFn }` (так сделано в демо). В Фазе 4: `t` в `ResolveErrorContext` и тот же тип в `defineList`.
6. **П. 6: что считается правкой.** `dirty` списка остаётся признаком состава. Значения полей строки в него не входят, как и раньше: правка поля делает dirty строку, но не список. Наверх поднимается именно состав вложенного списка (add, remove, setItems). Пагинированный список учитывает строки всех закэшированных страниц текущего запроса, как его собственный `dirty`. Считаются все списки, которыми владеет строка, в том числе объявленные в другом шаблоне (строка, открытая через `useForm(entity, template)`).
   **Первая версия п. 6 была медленной, и стандартные бенчи этого не показывали** (в них нет вложенных списков). Она пересчитывала `dirty` родителя обходом всех строк при каждом движении любого вложенного списка. Замер: 1 000 строк, у каждой вложенный список на 10 строк с резолвером, один компонент читает родительский список; загрузка всех вложенных списков — 39 ms на HEAD против 218 ms. После правки (множество `dirtyNested` и прямая проверка владельца) — 39 против 41 ms. Цифры в разделе «Цифры».
7. **«Успешный submit снимает dirty».** `submit()` ни в одной реализации baseline не двигает, ни у листьев, ни у списков: `dirty` после успешного submit остаётся. Цепочка чистая после `afterSubmit: (_r, { reset }) => reset()`, после `store.reset()` и после `reload()` вложенного списка. Тест «a successful submit that resets (afterSubmit) clears it along the whole chain; a submit alone does not» фиксирует оба случая. Поведение `submit()` не менялось.
8. **Демо.** Лента `/ssr/catalog` больше не шлёт `hasMore`: 12 строк по 4, последняя страница полная и отвечает `nextCursor: null`. Это сценарий находки 5, e2e «load more… nextCursor: null ends the feed» проверяет его в браузере. Тексты блока 2 `/ssr/runtime` и комментарии говорят «`usePalistor` запускает store после первого коммита».
9. **Тест конца ленты в срезе G** не добавлен: на ветке store без фикса, общий тест там красный. Он переезжает в контракт после merge `main` (план, п. 2).

### Кандидаты в «Migrating to 0.1» (продолжение списка раздела «SSR»)

5. **`usePalistor` запускает store после первого коммита.** Eager-резолвы и первый `onEnter` стартуют не в конструкторе. В первом рендере eager-список читает `resolveStatus: "idle"` (было `"pending"`), `loading` в обоих случаях `true`. Eager-группа с `suspense: true` в первом кадре показывает значения по умолчанию, а не fallback. Код с `new Palistor()` не затронут.
6. **Полный `store.reset()` не перезапрашивает вложенные списки и поля строк**, у которых резолв уже отработал. Нужен свежий запрос — `reload()` списка.
7. **`dirty` списка учитывает вложенные списки.** Правка внутри вложенного списка делает dirty список строки-владельца и форму. Код, который по `form.dirty` включает «несохранённые изменения», начнёт видеть такие правки.
8. **`nextCursor: null` — конец ленты** в `cursor` и `infinite`. Резолвер offset-ленты, который всегда отдаёт `nextCursor: null` вместе с `total` или `hasMore`, остановится после первой страницы: поле нужно не передавать. То же изменение идёт в `0.0.33`.
9. **`onError` получает `t`** вторым аргументом рядом с `notify`. Добавление, действий не требует.
10. **Предупреждение `pagination invariant` при смене ключа запроса** больше не пишется. Действий не требует.

### Найдено по пути

1. **store: `reset()` не отменяет прогон вложенного списка в полёте.** Строки приземляются после reset. Cube прогон отбрасывает. Расхождение было и раньше; общий тест «a list whose run is in flight starts over after the reset, on both» написан так, чтобы проходить на обеих реализациях.
2. **Внутри `act()` React не уступает управление** (в dev-сборке работа идёт через `workLoopSync`). Тест-воспроизведение п. 1 поэтому выключает `IS_REACT_ACT_ENVIRONMENT` и работает на настоящем планировщике: тяжёлые соседи (по 40 мс) заставляют transition уступить, тест меняет внешний store в этот момент и проверяет, что построено два store (рендер действительно отброшен), а резолверы вызваны по разу.
3. **Корневые списки после `reset()` сохраняют состав** (как в store): список, наполненный руками через `setItems`, остаётся dirty после reset. Не менялось; мешало только при написании тестов п. 6.
4. **Проба на типы `onError`:** `new Palistor({ config })` форму `onError` у группы не проверяет (конфиг выводится как есть), `defineList` проверяет. Отсюда разница в отличии 5.
5. **Строки пагинированного вложенного списка, восстановленные из persist-черновика, оставались без владельца** (`Pager.seed` не ставит связь, в отличие от `add`, приземлившейся страницы и `list.restore()`): они не удалялись каскадом вместе с владельцем. Проверка п. 6 «под какой строкой висит dirty-список» опирается на связь владельца, поэтому `cube/core/restore.ts` теперь её ставит. Тест: `cube/core/persist.test.ts`, «a draft's rows in a paginated nested list are owned by the row the list belongs to».
6. **store: `setItems` вложенного списка не принимает строки-объекты** (только id существующих сущностей, иначе бросает), Cube принимает. Общий тест про резолвер корня поэтому наполняет вложенный список через `add`.
7. **`server: true` в браузере — серверный режим целиком:** узел с `suspense: true` без данных бросает там ошибку отказа от SSR, а клиентский рендерер отдаёт её границе ошибок, а не Suspense. Это ручной режим для тестов и демо; отдельно в README не описано.
