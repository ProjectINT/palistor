# Эксперимент: Palistor на классах (Cube)

Дата: 2026-10-16. Набросок (с 2026-10-29 перенесён в [cube/core/](../cube/core/)): [index.ts в 90d8e67](https://github.com/ProjectINT/palistor/blob/90d8e67/experiments/index.ts).

Набросок проходит строгий tsc, а четыре сценария из README Palistor, прогнанные временным тестом, отрабатывают: реактивный isVisible, write pipeline с formatter и setter, optimistic и реальный resolve с перезапуском по зависимости, два списка поверх одного реестра сущностей.

## Мнение об идее

Идея хорошая, но выигрыш не там, где кажется. Сам Proxy занимает примерно две тысячи строк из шестнадцати. Громоздкость сидит в другом: в ручной машинерии зависимостей и в зоопарке видов узлов. Переход на классы даёт сократить объём, только если вместе с ним сделать две вещи.

- **Один рекурсивный примитив.** Лист, группа, список, элемент списка, шаг flow сейчас имеют по своему билдеру прокси и по своим веткам в ядре. В наброске это один класс плюс тонкий подкласс для списка. Resolve тоже один: на листе он резолвит информацию, на группе и списке резолвит кубики. Это ровно пункты 2 и 3 исходной идеи.
- **Автотрекинг через геттеры вместо карт зависимостей.** Каждый геттер кубика зовёт `track`. Одна глобальная переменная «кто сейчас наблюдает» закрывает вычисляемые флаги, зависимости resolve и трекинг чтений в useForm. У Palistor под это четыре разных tracking proxy, groupDepsMap, поле dependencies, топологическая сортировка и вся папка recompute. Ленивое мемо по версиям зависимостей заменяет их целиком.

Что при этом не исчезнет: pagination, persist, flows, filters, retry и типы. Это фичи, а не механизм. В новой архитектуре они становятся модулями вокруг ядра, но строки в них останутся.

## Слабые места наброска

- Трекинг в useForm без Proxy держится на том, что тело компонента выполняется синхронно до рендера детей. Чтения из компонентов без useForm попадут в набор последнего вызванного хука. Это лишний ререндер, а не баг, но точность Palistor теряется. Разумно оставить тонкий tracking proxy ровно в этом месте, остальной системе он не нужен.
- Spread полей в пропсы компонента перестаёт работать, потому что геттеры живут на прототипе. Нужен либо отдельный геттер `props`, либо own-enumerable геттеры.
- Зависимости асинхронного резольвера снимаются до первого await. Для чтений после него нужен values-объект, привязанный к наблюдателю, тот же трюк, что в createContextTrackingProxy, только на defineProperty.
- Зарезервированные имена детей остаются, как и сейчас: ребёнок с именем `submit` невозможен.
- Типизация через `CubeOf` набросана грубо, и типы в целом сильно не похудеют.

## Следующий шаг

Главный актив Palistor сейчас не код, а тесты: они и есть спецификация поведения. Разумный эксперимент на оценку идеи: портировать на Cube API один срез существующих тестов, например write pipeline и resolve, и посмотреть, сколько строк ядра понадобится, чтобы они позеленели.

## Фаза 0: перенос и baseline (2026-10-29)

План: [CubePlan.md](./CubePlan.md), Фаза 0.

### Перенос

Набросок разложен по `cube/core/` (`config`, `track`, `memo`, `registry`, `cube`, `listCube`), React-хук в `cube/react/useForm.ts`. Поведение ядра не менялось, кроме трёх мест:

- `cube.ts` не импортирует `ListCube`: подкласс регистрирует себя через `registerList`. Иначе модули `cube` и `listCube` импортируют друг друга, и `class ListCube extends Cube` падает на TDZ, если первым загрузился `cube.ts`.
- `instanceof ListCube` в `patch` и `getValues` заменён на защищённые `assign` / `snapshot`, которые `ListCube` переопределяет. Попутно `reset()` на сторе со списком больше не падает на `setItems({})`.
- Комментарии переведены на английский, как во всём пакете. `createStore`, `CubeOf` и `demo` удалены, сценарии `demo` стали `cube/core/core.test.ts`.

Фасад `cube/palistor.ts` даёт поверхность `new Palistor({ config })` поверх корневого кубика: `proxy`, `getValues`, `setValues`, `submit`, `reset`, `subscribeGlobal`, `getVersion`, `initialValues`. Остальные методы и опции бросают `NotImplementedError`. `cube/index.ts` повторяет все 12 рантайм-экспортов корня. Типы реэкспортируются из `store/`, поэтому код потребителя проверяется tsc одинаково против обеих реализаций.

### Расхождения, найденные в Фазе 0

1. **Submit и скрытые поля.** Store валидирует все листья, включая скрытые; исключение только для скрытых шагов flow (`filterHiddenFlowStepErrors`). Cube пропускает невидимые узлы в `collectErrors`. Контракт `surface.test.tsx` красный на `cube` ровно на этом. Решить в Фазе 1: баг Cube или намеренное изменение для документа миграции. Побочная находка: пример quick start в README (`passport.number` с `isRequired: true` внутри скрытой группы `passport`) на store не даёт отправить форму при оплате картой, пока не заполнен паспорт.
2. **`item.id` элемента списка.** В store это строка id сущности (README, раздел List proxy API). В наброске `id` — дочерний кубик. Шаг 2.1.
3. **API списков.** Store: `store.set(rows)` плюс `list.setItems(ids)`. Набросок: `setItems(rows)`. Шаг 2.1.
4. **`lazy: false` на списке.** Конструктор `Cube` запускает resolve внутри `super()`, до инициализации полей `ListCube` (`ids`, `cache`). Инициализаторы полей затем затирают оптимистичный результат. Фаза 1.
