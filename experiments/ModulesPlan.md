# План: модульные входы Palistor

Дата: 2026-11-15. Основа: Cube-ядро после Гейта 2 ([CubePlan.md](./CubePlan.md)), коммит `7e8b733`. Статус: не начато.

## Что решаем

Сейчас любой импорт из `palistor` тянет весь пакет. `import { Palistor, useForm } from "palistor"` для простой формы стоит 26,7 KB gzip — почти столько же, сколько приложение со списками, пагинацией и flow (27,6 KB). Цель: страница платит только за то, что импортирует. Форма без списков должна стоить около 12,5 KB gzip, а пагинация (треть пакета) должна попадать только на страницы, где она есть.

Ограничения:

1. Корневой вход `palistor` и существующие subpath-входы не меняются. Критерий drop-in из CubePlan (Гейт 3) остаётся в силе: потребители ничего не правят.
2. Поведение не меняется. Контракт (`cube/contract/**`, 975 тестов в проекте `cube`) остаётся зелёным без правок тестов.
3. Язык конфига не меняется: фичи включаются теми же ключами и функциями, что и сейчас.

В старом `store/` такая разбивка невозможна: списки, пагинация и flow там вплетены в `buildProxy` и `init`. В Cube фичи уже лежат отдельными файлами вокруг ядра, а для списков и flow в ядре уже есть точки подключения.

## Исходные цифры

Замер 2026-11-15: rolldown 1.1.4, `minify`, `react` внешний, `gzip -9`. Наборы получены сборкой корневого `index.ts`, в которой модули фич подменены пустыми заглушками. После настоящей разбивки цифры сдвинутся на сотни байт (код регистрации и тексты ошибок).

«Только формы» — это 12,5 KB, а не меньше, потому что реестр сущностей (`registry.ts`), логика строк в `cube.ts` и `hub.ts` и публичные узлы списка и flow в `node.ts` остаются в ядре. Их вынос в этот план не входит (см. «Что не делаем»).

## Как это выглядит для пользователя

```ts
// как сейчас: всё включено, существующий код не меняется
import { Palistor, useForm, defineList } from "palistor";

// по модулям
import { Palistor, useForm } from "palistor/core";
import { defineList } from "palistor/lists";
import "palistor/pagination";   // фича включается ключом конфига, своей функции у неё нет
import "palistor/filters";
import { defineFlow, defineStep } from "palistor/flow";
import { usePersist, localStorageDriver } from "palistor/persist";
```

| Вход | Рантайм-экспорты | Что подключает | Зависимости |
|---|---|---|---|
| `palistor` | все, как сейчас | все модули | — |
| `palistor/core` | `Palistor`, `useForm`, `usePalistor`, `PalistorProvider`, `usePalistorContext`, `useTranslator`, `useNotifier`, `useStoreContext`, `defineFieldMapping` | ничего сверх ядра | — |
| `palistor/lists` | `defineList` | списки (в том числе объявленные массивом) | — |
| `palistor/filters` | нет | блок `filter` списка | сам импортирует `lists` |
| `palistor/pagination` | нет | `resolve.pagination` | сам импортирует `lists` |
| `palistor/flow` | `defineFlow`, `defineStep` | flow | — |
| `palistor/persist` | `usePersist`, `localStorageDriver`, `sessionStorageDriver` | `store.persist` | — |

Все публичные типы доступны из `palistor/core`. Каждый вход-модуль дополнительно реэкспортирует типы своей фичи.

**Правило для пользователя: импорт модуля стоит в файле конфига или стора, который этим модулем пользуется.** ES-модули выполняют зависимости раньше тела файла, поэтому к моменту `new Palistor(...)` модуль уже зарегистрирован. Исключение — persist: `store.persist` создаётся при первом обращении, поэтому импорт `palistor/persist` может стоять там, где вызывается `usePersist`.

## Решения, которые принимаем сейчас

- **Корень остаётся полным.** Сделать его лёгким автоматически нельзя: фичи включаются содержимым конфига (список как массив — задокументированный синтаксис, ключи `resolve.pagination` и `filter`, свойство `store.persist`), а сборщик содержимого конфига не видит.
- **Подключение — это импорт, регистрация живёт на уровне модуля.** В ядре так уже сделано для списков и flow (`registerList`, `registerFlow` в `cube/core/cube.ts:29–38`). Тот же приём добавляется для пагинации, фильтров и persist. Класс `Palistor` один на все входы, пакет публикуется несобранным ESM, модули общие — поэтому смешивать входы в одном приложении безопасно.
- **Отвергнуто: модули на стор** (`new Palistor({ config, modules: [lists, pagination] })`). Вариант детерминированнее (нет глобального состояния), но требует перечислять модули в каждом сторе, меняет тип опций конструктора и не использует готовые швы.
- **Неподключённый модуль — ошибка с текстом, что импортировать.** Молчаливой деградации быть не должно. Сейчас flow без зарегистрированного модуля молча стал бы обычной группой.
- **Field mapping и реестр сущностей остаются в ядре.** Mapping стоит 0,65 KB. Реестр вплетён в чтение и запись значения листа.
- **Поле `sideEffects` в `package.json` не добавляем.** Разделение идёт по графу импортов, а не через tree-shaking: вход `palistor/core` просто не импортирует модули фич. Без поля сборщик считает, что побочные эффекты есть у всех модулей, и «пустые» импорты не выбрасывает. Неверное значение поля ломает регистрацию молча, а выигрыш от него — сотни байт.
- **Типы не разделяются и модули не проверяют.** Конфиг с `pagination` пройдёт tsc и без импорта модуля; ошибка будет при создании стора.
- **Старые subpath-входы** (`palistor/react/useForm`, `palistor/store/store`, `palistor/store/persist` и остальные) остаются полными: они реэкспортируют корень.

| `cube/react/useForm.ts:7` | значения `CUBE`, `STATE_KEYS` и другие через бочку `../core` | импорт из `../core/node` |
| `cube/index.ts:30` | драйверы persist через бочку | значения из входов (Этап 2) |

Что уже развязано и правок не требует:

- `cube.ts` не импортирует ни списки, ни flow.
- `persist.ts` обращается к пагинации и flow через `list.pager?.` и `hub.flows` (пустой массив без flow), импорты только типовые.
- Методы списка обращаются к пагинации и фильтру через `this.pager?.` и `this.filter?.`.
- `hub.persist` и `hub.map` уже допускают `null`; ядро зовёт `hub.persist?.clear()` (`cube.ts:485`).
- Конструктор `Persist` пустой (`persist.ts`: `constructor(private readonly hub: Hub) {}`), подписка появляется только в `enable()`. Поэтому ленивое создание безопасно.

## Этапы

Объём: около 150–200 строк правок в ядре, шесть файлов-входов, около десяти тестовых файлов, один скрипт.

### Этап 1. Развязка импортов

Поведение не меняется, входов ещё нет.

1. **Общие мелочи в ядро.** `stableStringify` → `config.ts`. `FLOW_STEPS_PROP` → `config.ts` (`flow.ts` и `cube/core/index.ts` продолжают её реэкспортировать). `ListState` → `cube/core/listState.ts`; `hub.ts` и `listCube.ts` импортируют оттуда.
2. **Списки.** В `listCube.ts` появляются `registerPager(factory)` и `registerFilter({ create, warnNested })`. `pagination.ts` и `filter.ts` вызывают их в конце файла — так же, как `listCube.ts` вызывает `registerList`. Значения `Pager`, `FilterCube`, `warnNestedFilters` из импортов `listCube.ts` уходят, типы остаются.
3. **Фасад.** `palistor.ts` импортирует из конкретных файлов. `instanceof FlowCube` → `flowRole`. `store.persist` — геттер: при первом обращении создаёт `Persist` через зарегистрированную фабрику (`registerPersist` в `hub.ts`) и кладёт его в `hub.persist`; без фабрики бросает ошибку с подсказкой.
4. **Ошибки.** `formCube` бросает ошибку, если у конфига есть маркер flow, а модуль не зарегистрирован. Новые тексты (с префиксом `[palistor]`, путь узла, точное имя импорта):
   - список: `"<path>" is a list, but the lists module is not loaded: import defineList from "palistor/lists" (or add import "palistor/lists")`;
   - пагинация: `list "<path>" uses resolve.pagination, but the pagination module is not loaded: add import "palistor/pagination"`;
   - фильтр: `list "<path>" has a filter block, but the filters module is not loaded: add import "palistor/filters"`;
   - flow: `"<path>" is a flow, but the flow module is not loaded: import defineFlow from "palistor/flow"`;
   - persist: `store.persist needs the persist module: import usePersist or a driver from "palistor/persist"`.
5. **Бочка.** `useForm.ts`, `defineFlow.ts`, `defineList.ts` и React-хуки импортируют из конкретных файлов. `cube/core/index.ts` остаётся для тестов ядра; в рантайм-коде `cube/` её импортов не остаётся.

**Гейт 1.** `npm run test:cube` (975 + 1 todo), `npm test`, `npm run typecheck:cube`, `npm run build` зелёные без правок тестов. Бенчи `cube/bench` в пределах разброса прогонов. Сборка одних `cube/palistor.ts` и `cube/react/useForm.ts` не содержит модулей `pagination`, `filter`, `flow`, `persist`, `listCube`.

### Этап 2. Входы и `package.json`

1. **Файлы входов** `cube/exports/{core,lists,filters,pagination,flow,persist}.ts`. Каждый импортирует свой модуль (это и есть регистрация), экспортирует рантайм с типами store (те же приведения `as unknown as typeof Store…`, что сейчас в `cube/index.ts`) и типы своей фичи. `filters.ts` и `pagination.ts` начинаются с `import "./lists"`.
2. **Корень собирается из входов.** `cube/index.ts` берёт значения из шести входов; список экспортов и имена не меняются. Так приведения типов живут в одном месте, а корень гарантированно подключает всё.
3. **`package.json`.** Шесть записей в `exports`: `./core`, `./lists`, `./filters`, `./pagination`, `./flow`, `./persist` → `dist/cube/exports/*.js` и `.d.ts`. Временный вход `./cube` и старые subpath не трогаем.

**Гейт 2.** `npm run build` зелёный; в `dist/cube/exports/` шесть новых входов; `dist/cube/exports/core.js` транзитивно не импортирует модули фич.

### Этап 3. Тесты модулей

Каталог `cube/modules/` (проект `cube` подхватывает `cube/**/*.test.{ts,tsx}`). Каждый файл импортирует только указанные входы. Vitest по умолчанию изолирует граф модулей на файл, поэтому файл, импортирующий один `core`, действительно работает без списков. `isolate: false` в `vitest.config.ts` включать нельзя.

**Гейт 3.** Новые тесты и весь контракт зелёные.

### Этап 4. Контроль размера в CI

Без этой проверки один случайный импорт незаметно вернёт пагинацию в ядро.

1. `rolldown` — в `devDependencies` (сейчас приходит транзитивно через vite 8).
2. `scripts/size.mjs`: для каждого набора из таблицы «Исходные цифры» создаёт виртуальный вход с импортами через карту `exports` из `package.json` (то есть проверяется опубликованная раскладка в `dist/`), собирает с `minify` и проверяет две вещи:
   - gzip не больше бюджета;
   - в сборке нет запрещённых модулей (для `core` — `pagination`, `filter`, `flow`, `persist`, `listCube`; для `lists` — `pagination`, `filter`; и так далее).
3. Бюджеты — в `scripts/size.budgets.json`: фактический размер после Этапа 2 плюс 3 %.
4. `npm run size` (после `npm run build`) и шаг в job `test` файла `.github/workflows/test.yml`. Скрипт печатает таблицу; она же идёт в README.

**Гейт 4.** `npm run size` зелёный в CI. Пробный `import "./pagination"` в `cube/core/cube.ts` роняет проверку (проверить один раз руками и откатить).

- `README.md` и `README.ru.md`: раздел «Modular imports» после «Installation» (таблица входов, пример, правило про место импорта, таблица размеров из `npm run size`). Строка в таблице Features. В разделах Lists, Pagination, Flows, Persist — по одной строке с модульным импортом.

### Этап 6. Пререлиз и проверка на потребителе

1. Пререлиз `0.1.0-cube.N` под dist-tag `cube`.
2. palirent без правок работает как раньше (корень полный).
3. Одна страница palirent без пагинированных списков переводится на `palistor/core` и нужные модули. После `next build` в чанке страницы нет пагинации (поиск по строке-маркеру, например `pagination.persist.maxPages`). Размер First Load JS страницы до и после записывается в журнал. Это проверка на настоящем сборщике приложения, а не только на rolldown.
4. Остальные страницы переводятся по желанию. Правило ESLint `no-restricted-imports` на корень `palistor` — только если потребитель хочет закрепить модульные импорты.

**Итоговый гейт.** Пакет с модульными входами опубликован под `cube`; корень ведёт себя как раньше; на сборщике потребителя страница на `palistor/core` не содержит пагинации; размеры наборов отличаются от таблицы «Исходные цифры» не больше чем на 5 %.

## Что не делаем

- **Лёгкий корень по умолчанию.** Это ломающее изменение (списки массивом, `store.persist`, ключи конфига перестанут работать без импортов). Кандидат на `1.0`.
- **Вынос реестра сущностей и логики строк из ядра.** Настоящий рефакторинг `cube.ts` и `hub.ts` ради 1–2 KB.
- **Вынос публичных узлов списка и flow из `node.ts`.** По оценке около 1 KB gzip (примерно 45 % файла). Возможный следующий шаг, когда появится `npm run size`.
- **Ленивая подгрузка (`import()`) внутри библиотеки.** Конструктор стора синхронный, асинхронное появление пагинации добавило бы промежуточные состояния. Постраничное разделение и так делает сборщик приложения.
- **Перевод `app-demo` на модульные входы.** До Фазы 4 CubePlan демо собирается и на store (`PALISTOR_IMPL=store`), где этих входов нет.

| Ленивый `store.persist` меняет поведение | красный срез F контракта | конструктор `Persist` пустой, ядро обращается через `hub.persist?.`; срез F обязан остаться зелёным |
| Цикл импортов после переносов (`ListState`, `registerPager`) | `Cannot access 'Cube' before initialization` при загрузке | функции регистрации объявляются в модуле ниже по графу (`pagination.ts` → `listCube.ts` → `cube.ts`), общие мелочи — в файлах без импортов ядра |
| Сборщик потребителя выбрасывает «пустой» импорт | ошибка «модуль не подключён» при наличии импорта | поле `sideEffects` не объявляем; проверка на palirent (Этап 6) |
| Один импорт из корня возвращает в чанк всё | размер чанка страницы | прямо сказано в README; `no-restricted-imports` по желанию |
| Две копии пакета в `node_modules`: модуль зарегистрирован в одной, стор создан из другой | ошибка «модуль не подключён» при наличии импорта | `npm ls palistor`; обычное лечение дублей |

## Открытые вопросы (решение за владельцем)

1. **Когда делать.** Рекомендация: после Гейта 3 CubePlan и до релиза `0.1.0`. Обкатка на palirent пройдёт на неизменном ядре, а новые входы попадут в README релиза. Начать раньше ничто не мешает (корень защищён контрактом), но тогда пререлизы для обкатки будут содержать рефакторинг Этапа 1.
2. **Имена входов.** В плане `palistor/flow` (по `defineFlow`) и `palistor/filters`. Альтернативы: `palistor/flows`, `palistor/filter`.
3. **Нужен ли вход-набор** вроде `palistor/lists-full` (списки, фильтры, пагинация одним импортом). В плане его нет: три строки импорта проще объяснить, чем ещё один вход.

5. Этап 5, затем пререлиз и проверка на palirent.
